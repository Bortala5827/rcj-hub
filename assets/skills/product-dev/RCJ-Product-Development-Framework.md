# RCJ Product Development Framework

> **RCJ 的「AI 产品操作系统」：先想清楚做什么、为谁做、留下什么，再让 AI 动手。**

RCJ 现在不是在写几个网站，而是在搭建一套「可孵化产品体系」。一年可能做几十个 vibe coding 产品。真正限制规模化速度的，不是开发速度，而是**有没有一套方法，让参与的每一个 AI（WorkBuddy / Trae / Codex …）都能理解同一套产品逻辑**。

核心思路——**注意，先做工具，不是先做生态**：

```
个人高频使用的小工具
      ↓
验证真实需求
      ↓
沉淀数据资产
      ↓
根据增长决定是否产品化
```

即：从一个**你自己真实会长期用**的小工具出发，而不是一开始就规划「生态」。现在几个方向之所以成立，共同点就是——都从你自己的真实需求出发。

本框架就是这个方法的载体。它和 `RCJ-产品生态总纲.md`（生态地图：RCJ 是什么、有哪些中枢）分工明确：

- **总纲**管「不能把产品做歪」——定义生态边界与品牌关系。
- **本框架**管「怎么把一个想法做成能长大的产品」——定义开发方法论。

两者互补，不互相灌内容。

## 一、产品第一性原理（First Principles）

每个项目开发前必须回答：

> **用户当前最大的痛点是什么？**

不要从「我要做一个 XX 网站 / APP」开始，要从「用户卡在哪」开始。

**硬性要求**：用一句话写下——

> 如果用户只能记住这个产品的一件事，那件事是：______

写不出来，就还没想清楚，先别写代码。

反例 vs 正例：

| 产品 | ❌ 错误起点 | ✅ 正确起点 |
|---|---|---|
| Training Hub | 做一个体测查询网站 | 帮用户持续记录、理解并提升身体能力，最终达到某个目标 |
| SoloSpeak | 做一个 AI 语音工具 | 解决独居者长期缺少表达练习与交流机会的问题 |
| FaceTalk | 做面试 APP | 解决用户无法低成本获得真实表达反馈的问题 |
| Exam Hub | 做一个刷题网站 | 把公开考试资料变成更高效、可本地优先的学习工具 |

### 产品关系链（现有方向不是孤岛）

SoloSpeak / FaceTalk / Exam Hub 三者其实在解决同一件事的不同阶段——「一个人如何提升面对真实场景的能力」：

```
日常表达训练           模拟交流训练           真实考试表达
SoloSpeak   ──►      FaceTalk     ──►      Exam Hub
（平时怎么保持           （怎么真正               （怎么准备
 表达状态）               开口表达）              考试）
```

- **Exam Hub**：我怎么准备考试？
- **FaceTalk**：我怎么真正开口表达？
- **SoloSpeak**：我平时怎么保持表达状态？

三者形成一条链，沉淀的资产也顺链复用（表达数据 → 面试反馈 → 考试口语）。

### SoloSpeak 的差异化（关键：不是「语音 AI」）

如果只是「语音 AI」，市场已经很多。SoloSpeak 的第一性原理其实是：

> **独居、远程工作、长期缺少交流的人，如何保持表达能力和语言状态。**

很多人不是不会说，而是：一天说不了几句话 → 表达欲下降 → 思维组织能力下降 → 长时间不交流导致社交状态变差。

所以 SoloSpeak 的核心不是「录音」，而是：

```
日常表达 → 声音记录 → 自我反馈 → 表达能力成长
```

它和健身打卡是同一类逻辑：别人记录跑步公里数、体重变化，你记录声音状态、表达能力变化。这是真正的差异化——**声音成长档案**。

## 二、产品定位原则

每个模块必须具备三件事：

### 1. 独立产品潜力
> 今天是功能，未来可以成为产品。

Training 与 SoloSpeak 是同一种逻辑——只是记录的维度不同：

```
SoloSpeak  →  声音成长档案
Training   →  身体成长档案

都是：建立档案 → 持续记录 → 分析变化 → 给出建议
```

Training 现在寄生在 Exam Hub 下，但它的终局应是独立产品：

```
现在：              未来：
Exam Hub           Training Hub
   └ Training        （独立产品 / 身体成长档案）
```

### 2. 模块调用能力
> 所有产品不能孤立，要能互相调用。

```
FaceTalk  ──调用──►  Exam Hub + Speak Series
Training  ──调用──►  消防考试 / 辅警考试
```

调用关系让单个产品变薄、整体变厚，避免重复造轮子。

### 3. 资产沉淀
> 每个项目必须想清楚：未来留下什么？

| 产品 | 沉淀的资产 |
|---|---|
| Training | 标准数据库、用户训练数据、训练方案 |
| Exam | 真题库、标签体系、**APKG / CSV 卡组（加工过的内容包 = 付费资产）** |
| Speak | 声音素材、语音交互经验 |

资产是穿越产品生命周期、能被后续产品复用的东西。

**资产里真正能收费的是「你加工过的内容包」（如 Exam 的 APKG / CSV 卡组），不是承载它的工具**（如 Anki 软件本身免费）。这条是 §四 变现原则的基础。

## 三、MVP 设计原则

### 最小可交付版本
不是「未来完整产品」，而是：

> **7 天～14 天可以上线验证的版本。**

先验证一个假设，再决定是否堆功能。

### Training V1 例子
**要验证的假设**：有没有人愿意每天 / 定期记录体能变化？（先跑通「记录」这个习惯，不急着分析）

V1 范围（已经足够）：
- 我的身体档案（基础信息 + 体测基线）
- 训练日志（每次训练的记录）
- AI 分析（基于日志给简单反馈）
- 目标倒计时（距目标的剩余时间 / 差距）
- 资源推荐入口（指向合适的训练资源）

❌ 不做：
- 社区
- 课程商城
- 复杂 AI 教练
- 教练入驻 / 撮合平台（见第六节风险）

### 通用 MVP 检查清单
- [ ] 能否在 14 天内上线？
- [ ] 是否在验证一个明确假设？
- [ ] 是否砍掉了所有「以后再说」的功能？
- [ ] 是否只依赖已存在的能力层 / 资产层？

### 成本与数据主权原则（MVP 阶段）
前期都还没收入，原则：**尽可能不花钱**。具体落地：

- **MVP 不依赖服务端数据库**。用浏览器本地存储（IndexedDB / localStorage），零服务器成本。
- **本地存储的边界要知道**：刷新页面、关页面都不丢；但用户一旦「清除浏览数据 / 清缓存」，数据就没了——这不是 bug，是浏览器机制。
- **必须有「导出 / 导入」作为安全网**：让用户把数据导成 TXT / CSV / JSON 自己备份，数据主权归用户。也让数据可迁移、不锁死在某一台浏览器。
- 与 Speak Series 模式一致：SoloSpeak 的声音日志同样是「本地优先 + 可导出」（TXT/MD/JSON），Training 直接复用这套思路。

## 四、产品成长路线

统一路线：

```
MVP → 用户验证 → 数据沉淀 → 模块增强 → 商业化 → 独立产品
```

Training 的例子：
- 阶段 1：Exam Hub 内的工具
- 阶段 2：职业体能助手
- 阶段 3：AI 体能成长平台

每个阶段结束的标志不是「功能做完了」，而是「验证了下一阶段成立的前提」。

### Training 的商业化路径（分三阶段，别急着做平台）

**第一阶段｜自己用 + 考生使用**
入口在 Exam Hub，覆盖：消防 / 辅警 / 入伍等招录人群。

**第二阶段｜训练服务转化**
```
线上记录工具 → 发现差距 → 产生专业训练需求 → 谢求知团队
```
闭环自然：用户不是主动找机构，而是在使用中发现「我还差很多」。

**第三阶段｜扩大人群**
职业招录 → 青少年体育 → 家庭运动管理（市场更大）。

### 第三方教练平台的风险（重点：不要早做）

一旦做「教练入驻平台」，性质从工具变成平台，立刻新增：教练资质审核、安全责任、服务纠纷、用户隐私、未成年人保护。

分阶段替代方案：
- 初级：推荐优质教练名单 + 联系方式（类似导航）
- 中级：RCJ 认证训练伙伴
- 高级：才考虑平台撮合

### 现在真正该做的：先跑三个「小闭环」

不要急着想商业生态，先验证习惯是否成立：

- **SoloSpeak**：有没有人愿意每天记录？
- **FaceTalk**：有没有人愿意练表达？
- **Training**：有没有人愿意记录体能变化？

其中任意一个形成习惯，它自然会长成产品。

### 通用变现原则：工具免费、数据资产收费

变现的逻辑要反过来想——**收费的对象是「你生产的数据资产」，不是承载它的工具**。

- **工具 / 软件免费分发**：Anki 这类阅读器（AnkiDroid / 桌面版）本身开源免费，直接给下载链接或网盘资源即可，不从中收钱。
- **数据资产收费**：CSV / APKG / 题库卡组这类「你整理、标注、加工过的内容包」才是付费点——复制成本极低、边际成本为零，最适合做低价数字商品（闲鱼 / 公众号私域复购）。
- 这条把 §二 的「资产沉淀」与「商业化」打通：先免费把工具送到用户手里（获客），再靠数据资产变现（转化）。

Exam Hub 实例：刷题站本身可免费用（且**故意限量范围**当预览）→ 导出 Anki（软件免费，给链接）→ 导出的 **APKG / CSV 卡组 / 离线 HTML 题库**作为数据资产收费。

**交付分层铁律（防止"免费版太完善反而卖不动"）**：
- 免费在线 = **预览 / 获客**，用「范围」限制（限城市 / 限批次 / 限题型），不靠降低体验质量。
- 付费离线 = **主交付物**，卖点是「完整覆盖 + 数据自有 + 便携不依赖服务器」的**正向框架**，不拿"线上网络不稳定"当恐惧钩子（差异弱且不诚实），仅在 FAQ 诚实说明。
- Anki / 各种导出格式 = **附加增值**，不构成付费门槛；核心付费物是加工过的数据资产本身。

**窗口期打法（变现节奏）**：招聘类产品的成交高度依赖 招聘公告 → 笔试 → 面试 的 2–4 周热窗。提前备好卡组、公告即上架，比"常年铺货"转化高得多。优先级随招聘频率与基数动态调整（如 辅警 > 消防 > 三支一扶 > 民警）。

（注：iOS 版 AnkiMobile 由官方收费，与我们的数据资产无关；免费分发只指 AnkiDroid / 桌面版。）

## 五、技术架构原则（三层）

每个产品必须分三层，依赖方向单向：

```
┌─────────────┐
│  产品层       │  用户看到的应用（training-hub）
└──────┬──────┘
       │ 调用
┌──────▼──────┐
│  能力层       │  AI / 算法 / 组件（training-engine, rcj-audio-core）
└──────┬──────┘
       │ 读写
┌──────▼──────┐
│  资产层       │  数据 / 素材 / 知识库（training-assets）
└─────────────┘
```

规则：
- 产品层依赖能力层，能力层依赖资产层；**反向禁止**。
- 能力层跨项目复用（如 Speak Series 共用 `rcj-audio-core`），不每项目重写。
- 资产层与具体产品解耦，可被多个产品读取。

## 六、AI 开发协作规范

给 WorkBuddy / Trae / Codex 的开发任务，必须附带或指向 `PRODUCT_RULES.md`。该文件至少包含：

- 产品定位
- 用户画像
- MVP 范围
- 技术约束
- 禁止事项

### 禁止事项（Anti-patterns）
AI 不得擅自做以下事，需先与用户确认：
- **定位漂移**：偷偷把工具做成平台、把单机做成社交。
- **功能堆叠**：在 MVP 阶段加「以后可能用得到」的功能。
- **仓库边界混乱**：把 A 产品的逻辑写进 B 产品的仓库。
- **重复开发**：已有能力层 / 资产层可复用时，重新造一遍。
- **过早平台化**：在 MVP / 验证期引入「入驻 / 撮合 / 社交」等平台机制（如教练入驻），性质从工具变平台，责任面骤增（见第四节风险）。

### AI 不应擅自
- 新建 GitHub 仓库（先问用户）。
- 扩大约定范围（如把本地优先改成服务端）。
- 引入未授权的新依赖。

### 工作区与产出物纪律（Workspace Hygiene）

> 原则：**仓库是产品的家，不是 AI 的草稿纸。**

**1. 不动 `_repos/`**
- `products/_repos/` 下每个仓库只放**属于该产品本身**的文件。
- AI 生成的草稿、脚本、截图、导出数据、实验产物、临时中间文件，**一律不得**写进任何仓库目录。
- 确需修改仓库内文件时，只改与当前任务**直接相关**的那几个文件，不顺手重排目录、不批量改名、不删无关文件。

**2. 生成物统一进 `projects/`**
- 所有 AI 产出的非仓库内容，放 `products/projects/<用途名>/`。
- **一个用途一个文件夹**，不混装。示例：
  ```
  projects/
    wechat-xhs-content/      公众号+小红书内容生产（meta.json → build.js → 截图）
    training-mockup/         Training Hub 界面草图
    exam-cover-2026-08/      题库封面图批次
  ```

**3. 命名规范（能一眼看懂）**
- 文件夹名 = **用途**，不是「新建文件夹 / test / tmp / 未命名 / output」。
- 文件名 = **内容语义**，需要区分批次时加日期 `YYYY-MM-DD` 或版本 `v1 / v2`。
  - ✅ `深圳辅警面试-封面-2026-08-10-v2.png`
  - ❌ `image1.png` / `最终版最终版.png`
- 一律用可读中文或英文小写连字符，不用空格、不用乱码后缀。

**4. 每个生成物文件夹必须有 `README.md`**
至少一句话说清：**这是什么 / 给谁用 / 怎么用 / 来源与生成时间**。没有 README 的文件夹视为垃圾，随时可清理。

**5. 用完即清**
- 一次性中间产物（临时 HTML、调试截图、爬取缓存）任务结束即删，不留在工作区。
- 不确定要不要留的，问用户，不要默认堆着。

## 八、一句话理念与项目纪律

> **RCJ 不追求一次性打造完整产品，而是通过模块化 AI 开发，先跑个人高频小工具、验证真实需求、沉淀数据资产，再根据增长决定是否产品化。**

### 项目数量纪律（最重要的一条）

现在项目已经不少，后面最重要的是**控制新增项目数量**。一个新的模块 / 产品，最好先满足以下四点再开发：

1. **自己长期使用**（不是「别人可能需要」，是「我自己每天 / 每周用」）；
2. **有明确用户痛点**（能一句话说清卡在哪）；
3. **能沉淀数据资产**（留下可复用的东西，不只是功能）；
4. **能被现有生态调用**（不是又起一个孤岛）。

满足这四点，开发价值才高。Training Hub 基本符合。

> 你现在最大的优势不是代码能力，而是不断发现「某个细分人群的一个真实问题」，然后用 AI + Web 快速做 MVP。这正是独立开发者目前最有效的路线——但前提是不被项目数量拖垮。

## 九、增长层（自媒体矩阵）

产品打磨好之后，自媒体是**低边际成本的增长层**，不是独立业务：

- **前期**投入时间把产品做扎实、把内容管线（草稿填充、素材库）跑通；
- **后期**产品稳定，自媒体变成每天定时的轻运营，不占大量精力。

平台分工（已拍板）：**微信公众号第一优先级**（私域主阵地，长文 + 贴图，Playwright 仅填草稿、人工发布）；小红书做合规纯内容（不主动导流）；视频号用自有录屏讲过程（简洁无特效）。

> 🔴 红线：自媒体只做**获客与私域沉淀**——不碰自动发布、不夸大能力、不站外导流。完整策略见 `product-dev/Content-Growth-Strategy.md`。

## 十、RCJ 产品开发哲学（Principles Manifesto）

> 上文 §一～§九 是「操作规范」（怎么做），这一章是「原则全集」（为什么这么做）。新增仓库或让 AI 开发前，先读这一章对齐价值观，再回到对应操作节落地。

### 1. 第一性原理（First Principles）
> 用户有什么真实需求？当前解决方案有什么不足？我能否用更低成本、更高效率的方法解决？

不要从「我要做什么产品」开始，而从「用户卡在哪」开始。→ 详细反例/正例与产品关系链见 §一。

### 2. MVP 最小交付（Minimum Viable Product）
> 先验证价值，再完善功能。

MVP 目标是快速上线、快速使用、快速反馈、快速迭代。→ 范围与检查清单见 §三。

### 3. 模块化产品（Modular Product Design）
RCJ 不追求一次性打造大型平台，采用「模块化开发 + 独立成长」：每个模块既能作为其他产品的调用能力，也具备未来独立成产品的可能。

```
当前：                       未来：
Exam Hub                   RCJ Hub
 ├ 消防考试                  ├ Exam Hub
 ├ 辅警考试                  ├ Speak Series
 ├ FaceTalk                  ├ Training Hub
 └ Training Hub             └ 其他创新产品
```

### 4. 产品 / 能力 / 资产 三层模型（生态级）
与 §五 的「技术三层」互补——这里是**实体级**的三类东西：

| 层 | 是什么 | 例子 |
|---|---|---|
| **产品 Product** | 直接面向用户的应用 | Exam Hub / FaceTalk / SoloSpeak / LetOut / Training Hub |
| **能力 Skills** | 沉淀的开发与运营能力 | AI 工作流、Prompt、自动化脚本、Playwright 自动化、Vibe Coding 方法、部署经验 → 凝结为 `RCJ Skills` |
| **资产 Assets** | 长期积累、可重复调用 | 题库数据、音视频素材、文案素材、图片资源、知识库 → 如 `RCJ Media Assets` |

> 产品解决用户问题，Skills 提升生产效率，Assets 提供长期价值。三者解耦、可独立复用。

### 5. 轻资产原则（Lean Asset）★新立
> 用最低成本验证最高价值。

优先采用：开源资源、云服务、免费工具、自动化流程；不提前投入大量资金建设重资产系统。与 §三「成本与数据主权原则」同源——MVP 阶段一切以「零/低边际成本」为底线。

### 6. 窗口期优先原则（Opportunity Window）★新立
> 产品开发不仅看长期价值，也盯当前机会窗口。

当出现政策机会、市场需求、用户热点、变现机会时，优先投入资源。如消防 / 辅警 / 三支一扶等招录内容属于明确的需求窗口，优先完善题库、学习资源、工具入口，快速验证市场。→ 具体打法见 §四「窗口期打法」。

### 7. 产品赛马机制（Product Competition Mechanism）★新立
> 多模块并行探索，数据决定资源分配。

类似大厂内部创新机制——不是平均分配资源，而是多个方向同时验证：

```
产品A ┐
产品B ├─► 用户反馈 ─► 数据表现 ─► 重点投入优秀项目
产品C ┘

表现好：增加开发资源 / 加大推广 / 独立品牌化
表现一般：保留资产 / 降低投入 / 等待机会
```

避免「每个都养、每个都不强」。

### 8. 数据驱动决策（Data Driven）★新立
> 不能只靠感觉判断产品价值。

建立统一数据后台（如 `rcj-hub/admin.html` 已聚合 Speak Series 本地数据），持续观察：访问量、用户来源、使用频率、留存、热门功能。未来据数据调整推广重点、产品方向、资源投入。例：Training 使用量增长 → 加投；某模块无人用 → 降维护成本。

### 9. 自我使用原则（Dogfooding）
> 优先开发自己真正需要用的产品——自己就是第一批用户。

SoloSpeak 自己每天用、Training 自己记录、FaceTalk 自己练表达。长期使用才能发现真实问题。→ 这也是 §八「项目数量纪律」的第一条（自己长期使用）。

### 10. AI 协作开发（AI Native Development）
AI 不只是代码生成工具，更是产品设计伙伴。流程：需求发现 → 第一性原理分析 → MVP 设计 → AI 辅助开发 → 用户测试 → 持续优化。所有 AI（WorkBuddy / Trae / Codex）遵循本框架统一规范。→ 详见 §六。

### 11. 方法论资产沉淀（Methodology Asset）
每次开发不只产生产品，同时沉淀产品思考、开发流程、避坑经验、AI 使用方法、自动化流程，形成 `RCJ Skills` 的方法论资产（即本 `product-dev/` 文档集）。未来可通过自媒体 / 公众号 / 视频号输出「从 0 到 1 用 AI 开发产品的方法论」。

### 12. 长期发展路径
```
发现需求 → 快速 MVP → 个人使用验证 → 小范围用户验证 → 数据增长 → 资源倾斜 → 独立产品 → 生态连接
```
最终目标不是同时维护大量项目，而是通过模块化孵化机制，不断发现有潜力的产品，让优秀模块成长为独立业务。

---

> **RCJ 核心理念总结**：用 AI 降低产品开发成本，用模块化提高复用效率，用数据决定发展方向，用长期资产积累形成个人创新生态。
