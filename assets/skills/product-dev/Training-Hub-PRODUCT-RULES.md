# Training Hub · PRODUCT_RULES

> 框架模板实例（见 `RCJ-Product-Development-Framework.md` 第七节）。v0.0 规划中，本文件用于锁定 MVP 范围、防止定位漂移。

## 项目定位
个人「身体成长档案」工具——帮用户持续记录、理解并提升身体能力，最终达成某个训练目标。与 SoloSpeak（声音成长档案）同逻辑，只是记录维度不同。

## 核心用户
- **第一用户：自己（高频自用）**——每天 / 定期记录体能状态。
- **第二波：招录考生**（消防 / 辅警 / 入伍等）——通过 Exam Hub 入口进入，用训练日志记录备考体能。

## 第一性原理
> 如果用户只能记住一件事：*我今天的身体状态，和上次比，变好了还是变差了。*

不是「体测查询网站」，不是「训练平台」。是一个**成长日志**。

## MVP 功能（v0.1，接口特别小）
先只验证一个假设：**有没有人愿意每天 / 定期记录体能变化？**

✅ 只做：
- **建档**：基础信息 + 体测基线（身高 / 体重 / 几个核心指标）。
- **训练日志**：每次训练的简单记录（日期、做了什么、感受 / 数值）。
- **目标倒计时**：距目标的剩余时间 / 当前差距。
- **资源跳转（导航式，不做聚合）**：用户输入地区（如「广东」）→ 返回该地区题库 / 资源网址 → **用户自行跳转**。不下载、不合并各地数据库。
- **数据导出 / 导入（安全网，必做）**：一键导出档案 + 日志为 TXT / CSV / JSON，用户自己备份；支持导入还原。数据主权归用户，不锁死在某一浏览器。

❌ 不做（明确禁令）：
- 社区 / 课程商城 / 复杂 AI 教练。
- 教练入驻 / 撮合平台（性质从工具变平台，责任面骤增，见框架第四节）。
- 把各地考题库拉成本地图谱做标准查询（后期再说，复杂度高）。
- **服务端数据库 / 账号系统**：MVP 阶段不花钱建后端，用浏览器本地存储（见下）。

## 数据存储（本地优先，零成本）
- **存储方式**：浏览器本地存储（IndexedDB，参照 Speak Series 技术栈），**不依赖任何服务端数据库** → 前期零服务器成本。
- **边界要知道**：刷新页面、关闭页面都不丢；但用户一旦「清除浏览数据 / 清缓存」，数据会丢失（浏览器机制，非 bug）。
- **靠导出兜底**：正因为清数据会没，所以「导出 / 导入」不是锦上添花，而是 MVP 的必备项——让用户把数据握在自己手里。
- 与 SoloSpeak 一致：声音日志同样是「本地优先 + 可导出」，可直接复用其导出逻辑。

## 后续路线
```
MVP（个人生长日志）
   ↓ 验证：记录习惯是否成立
数据沉淀（身体档案 + 训练日志）
   ↓
模块增强（AI 分析：基于日志给简单反馈）
   ↓
商业化（三阶段，见下）
   ↓
独立产品（身体成长档案）
```

## 调用模块
- **被调用（入口）**：RCJ Exam Hub 收纳 Training 入口，覆盖招录人群。
- **调用（资源）**：地区 → 题库网址 的映射（轻量 lookup，非聚合）。后期可调用 Speak Series 做「表达 + 体能」联合档案。

## 数据资产
- 标准数据库（体测指标定义）。
- 用户训练数据（档案 + 日志，本地优先 + 可导出，数据主权归用户）。
- 训练方案（后期沉淀）。

## 商业模式（三阶段，平台化后置）
1. **自己用 + 考生使用**：入口在 Exam Hub，覆盖消防 / 辅警 / 入伍。
2. **训练服务转化**：线上记录 → 发现差距 → 产生专业训练需求 → 谢求知团队（闭环自然）。
3. **扩大人群**：职业招录 → 青少年体育 → 家庭运动管理。

第三方教练：初级只做「名单 + 联系方式」导航；中级 RCJ 认证伙伴；高级才考虑撮合。
